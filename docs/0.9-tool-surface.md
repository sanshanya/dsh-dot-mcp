## 1. 要解决的问题（先把话说准）

外部审查稿的主张是"23→14 个工具"。这条**不是**本设计的目标，理由是三方一致的数据：

- 工具个数的直接成本只是"名字 + 结构"——隐藏 7 张名片今天只能省 4,813 字符；
- **一半的体积是散文**（描述 7,349 + 参数说明 2,704 = 10,053，占 50%）；
- **枚举只占 0.7%**（131 字符），"砍枚举省字"是误判；
- 真正的痛点是**选择歧义**（同一意图两扇门）与**每轮重复支付的固定成本**。

因此本设计的两个目标：

1. **固定成本**：core 档 `tools/list` ≤ **11,000** 字符（相对 19,748 降 ≥44%）。
2. **选择歧义**：同一意图只留一个入口，且默认档里的工具名字不得出现在被隐藏工具的描述里。

> 副目标（不属于本版本承诺）：单次调用响应体积。`get_result` 已有 `total_max_chars`，其余读工具见 §7 F3。

## 2. 机制：三个档位是**权限面**，不是显示过滤器

**已实测的硬约束**（C1 独立复核，本档采信）：MCP SDK 的 `ListTools` 按 `tool.enabled` 过滤（`@modelcontextprotocol/sdk/dist/esm/server/mcp.js:70`），
`CallTool` 对 disabled 工具抛 `-32602 Tool X disabled`（同文件 `:102-109`），未注册则是 `not found`；
且分发处理器不可二次覆写（`protocol.js:903-907`）。

⇒ **"旧接口保留但默认只展示新接口"在现 SDK 下不成立。** 档位一旦收面，旧名字就是不可调用。

| 档 | 工具数 | 面向 | 默认值 |
|---|---|---|---|
| `legacy` | 22 | 已部署客户端 | **0.9.0 的代码默认** |
| `core` | 15 | 新装 / 常规路径 | 面板一键切换（新装引导推荐） |
| `full` | 22 | 排障、密钥、回执 | 需显式选择 |

- **0.9.0 不翻转默认档。** 语义化版本下"默认可见面收窄"是破坏性变更，即便可配置回；升级用户的 `tools/list` 必须逐名字不变。
- `surface` 是 **volatile** 字段：`http.ts` 每请求新建 server，翻档后下一次 `tools/list` 立即生效（stdio 单例需重启，`index.ts:56`，需在文档写明）。
- **规则 D1（档位只改可见性，永不改语义）**：同一名字在任何档里行为、入参、响应必须逐字节相同。禁止"在 core 档下顺手收紧某个参数"。

### 3.1 为什么不合并两个 wait（撤回本方早前主张）

本方曾据"两 wait 同签名同返回"主张合并为 `wait_events`。**该判断被推翻**：

| | `dsh_wait_goal` | `dsh_wait_until_action_required` |
|---|---|---|
| 引擎 | `nativeWait`（goal 相位机） | 状态轮询 `while (isActiveStatus(status))`（`waits.ts:81`） |
| 上限 | 30s（`clampWaitSeconds`） | 300s |
| 前置 | 需要原生 goal | 不需要 goal |
| 语义 | 等 goal 推进 | 等会话脱离 running/queued |

两者是**不同意图**，合并会强行统一引擎与上限。保留两扇门，只修名字带来的误解。

### 3.2 为什么不合并 start/pause/resume/stop

四个动词对应四种锁与中继姿态，实测：

- `start_goal`：武装监督循环 + 抢 workspace 锁（`bridge.ts:1267-1332`）
- `pause`：`nativePause` → `relays.failClosed` → `agent.cancel` → `whenIdle` → `releaseUnusedWorkspaceLock`（`bridge.ts:1145-1169`）
- `resume`：重取锁并重臂（`bridge.ts:1376`）
- `stop`：fail-closed 停车 + 清 goal + 释放锁（`bridge.ts:1419-1443`）

塞进一个 `action` enum = 让权限边界靠参数猜。

## 5. 预算与测量（唯一的裁决工具）

新增 `scripts/surface-cost.mjs`：

```
node scripts/surface-cost.mjs --surface legacy|core|full [--mode static|served] [--json]
```

- `static`：用 `createMcpServer(stubBridge, tier)` 直接取投影；
- `served`：对活桥 `initialize` + `tools/list`，量原始响应字节；
- 两者差 ≥2% 即判脚本失效（M1）。

**预算表（core 档，实测基准）**：

| 口径 | 字符 | 相对 19,748 |
|---|---:|---:|
| 今日全量 | 19,748 | — |
| core-15 仅隐藏 7 张名片 | 14,935 | −24.4% |
| **+ 描述 ≤175 / 参数说明 ≤70（本档目标）** | **10,895** | **−44.8%** |
| 再剥离 `$schema` 样板（可选杠杆，实现待验） | 10,115 | −51.2% |

**ratchet 规则**（写进 CI）：任一工具 > 1,100 字符失败；任一工具描述 > 260 字符失败；core 合计 > 11,000 失败。**只准降不准升。**

> 预算 11,000 是推导值而非整数强迫：结构性下限（删光所有散文）为 5,908，散文额度 9,027；desc≤175/param≤70 的实测投影为 10,895。曾提议的 8,460 **算术不可达**（C1 A3 与本档独立复算一致）。

## 7. Falsifier（每条都必须能真红）

| # | 主张 | 证明它错了的观测 |
|---|---|---|
| M1 | 静态投影可复现 served 体积 | 两模式差 ≥2% |
| F1 | core ≤ 11,000 字符 | `served` 超预算 |
| F2 | 读合并能力中性 | 对同一会话，`detail='session'` 的响应键集 ⊇ 今日 `get_session` 的键集；且 `detail='status'` 与今日 `get_task_status` 键集相等 |
| **F3** | **合并不得抬高最热路径体积** | `detail='status'`（默认）响应体积 > 今日 `get_task_status` 的 ±10%（基线实测 ≈450 字符） |
| F4 | 档位热切换（http） | 翻 volatile 后下一次 `tools/list` 不变 |
| F5 | core 档内所有文字不指向不可用名字 | 扫描 `tools/list` 全部 description/参数说明 + 全部响应，出现 hidden 名即红 |
| F6 | 档位不改语义（D1） | 同一输入两档返回不同结果 |
| F7 | 每档每个工具都被真实驱动 | golden 在 core 档跑出 `driven ≠ CORE` |
| F8 | 省字没砍功能 | core 与 legacy 的同名工具，参数名集合逐字相等（AST 比对） |
| F9 | 合并保持 workspace 锁释放副作用 | 构造锁占用会话，`detail='status'` 轮询终态后锁仍未释放 |
| **F10** | **选错工具率不上升** | 20 条固定剧本的 first-choice accuracy，core 档低于 legacy 档 ≥1 条即红（见 §8） |

## 8. 属于本版本、但不属于"工具面"的一项

**选择正确率必须被测**。C 席指出：整套方案最初的动机是"模型选错工具"，而所有 falsifier 测的都是字节、集合、锁、覆盖——**没有一个测选错**。

本版本附带最小可行测量：

- 20 条固定剧本（读会话 / 启动 goal / 审批 / 回答提问 / 取消回合 / 等 goal / 等会话 / 读结果 / 列会话 / 发消息 …）
- 每条记录：模型第一次选择的工具名、是否正确、是否发生"调用被拒后重试"
- 分别在 `legacy` 与 `core` 档跑同一组剧本，比较 first-choice accuracy
- **判据**：core 档不得低于 legacy 档 1 条以上；若下降，压缩策略回退到 desc≤260

## 9. 本轮 2+2+1 的完整记录

| 席 | 产出 | 关键结论 |
|---|---|---|
| P1 | 三档（legacy/core/full）+ 新名字 `inspect_session`/`wait` + 预算 8,460 | 发现 `create_goal` 与 `start_goal` 同权、`next_tool_call` 写死、pause 丢字段 |
| P2 | 两档 + 零新增名字（`detail` 合并）+ 预算 11,000 | 发现 `isActiveStatus`、四动词四种锁姿态、冻结名单有副本、文档漂移 |
| C1 | 17 条攻击 | **8,460 算术不可达**；F2 恒红；退路=截肢；`$schema` 5.8% 免费杠杆；P1 自评 8 分过高（给 6） |
| C2 | 15 条攻击 | **核心痛点零测量**；轮询税 450→5,866，breakeven 2.08 次；core 档 4 处文字诱导隐藏名 |
| 裁判 | 本档 | 采 P2 的机制 + 11,000 预算；撤回本方三处主张（见下） |

**被证伪的本方主张（必须留痕）**：

1. "429 全是端口号/哈希" → 实为**时间戳毫秒段**为主，无一条是 HTTP 状态。
2. "pause/resume 不碰锁" → pause 实际 `failClosed` + 取消回合 + 释放未用锁。
3. "两个 wait 同实现可合并" → 引擎、上限、前置条件均不同。

**两席对"读合并用新名还是复用旧名"裁决相反**：C1 主张新名（N1），C2 主张复用（`detail`）。
裁判采纳 C2：N1 是单向规则（同名 ⇒ 同形状），加可选参数且默认保留今日形状**不删字段**，不违反 N1；
且 `get_result` 已有 `detail` 先例。代价是放弃"legacy 逐字节冻结"这条自设约束——**接受**，因为它从未被仓库使用过。
