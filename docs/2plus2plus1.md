# 2+2+1：两稿、两审、一档

> 本文是仪式说明，不是流程装饰。凡是"方案制定/修改"必须走完；凡是不走完的，输出只能叫草稿。

## 一、形状

```
设计阶段    P1 独立稿 ─┐
                       ├─▶ 汇总（裁判）──▶ MERGED ─┐
           P2 独立稿 ─┘                             │
                                                    ├─▶ 冻档（裁判写）
审查阶段    C1 攻击 ───┐                             │
                       ├─▶ 判（裁判）───────────────┘
           C2 攻击 ───┘
```

- **P1、P2 不共享上下文**：同一份简报，各自独立作业，不许串题。
- **C1、C2 只攻击，不给替代方案算不合格**。
- **裁判是"一"**：不数票，自己复算关键数字；两席冲突时用证据裁，不用多数决。

历史上有三种说法被混用过（"两稿"、"P1/P2 + C1/C2 + 判"、"两次评估 + 两次对抗 + 一次裁"）。
**唯一规范形态就是上面这个**：设计两稿并行，审查两攻并行，一档收口。

## 二、四条铁律

1. **对抗性审查必须在隔离上下文里做。** 写过设计的人不能审自己的设计——他会被自己的理由说服。
2. **证据打败意见。** 每条主张必须带 `文件:行`、命令输出或可复算数字。没有证据的攻击记为"意见"，不进判词。
3. **P 与 C 不共享上下文。** 共享了就不是对抗审查，是自查。
4. **主张强度 ≤ 证据强度。** 拿到"未发现 X"就说"未发现 X"，不许说"不存在 X"。
   （本法则的来源是一次真实事故：把"未发现真实限流"说成"40 处 429 全是端口号"，事后全量核对发现多数是时间戳毫秒段。）

## 三、两次冻档，别混成一次

| | 设计冻档 | 发布冻档 |
|---|---|---|
| 时机 | 实现**之前** | 全绿**之后** |
| 判据 | 证据是否充分、falsifier 是否可执行 | `npm test` + release + golden + 本阶段 falsifier |
| 不看什么 | **不看测试绿不绿**（此刻还没代码） | 不看"看起来没问题" |

把两者混成一句"不绿不进档"，会让设计阶段被测试状态绑住——而设计阶段根本没有测试可跑。

## 四、每个冻档必须有的三行

1. **主张**：一句话，可被证伪。
2. **falsifier**：什么观测能证明它错了。写不出观测的主张，不许进冻档。
3. **回滚**：一行能执行的配置/提交回退。

## 五、留痕：错的判断比对的判断更值钱

冻档里必须有一节记录**本轮被证伪的主张**，包括裁判自己的。

理由不是自罚，而是：被证伪的判断携带的信息量最大——它标出了"我们的直觉在哪里系统性偏了"。
只记录"最后正确答案"的文档，下一个人会在同一个地方再摔一次。

## 六、本轮（0.9.0 工具面）的实例

| 席 | 谁 | 结果 |
|---|---|---|
| P1 | 规划席 | 三档 + 新名字方案，预算 8,460 |
| P2 | 规划席 | 两档 + 零新增名字方案，预算 11,000 |
| C1 | 反方席 | 17 条攻击，证明 8,460 算术不可达 |
| C2 | 反方席 | 15 条攻击，证明核心痛点零测量 |
| 一 | 裁判 | 采 P2 机制 + 11,000；撤回本方 3 处主张 |
