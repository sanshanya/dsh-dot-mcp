## 阶段闸门（每阶段统一）

```
两稿(P1/P2) → 汇总(裁判) → 两审(C1/C2) → 冻档 → 实现 → 全绿
```

**全绿** = `npm test` + `npm run test:release` + `npm run test:golden` + 本阶段专属 falsifier。
缺一不可；**不绿不进档**（这一条只管发布，不管设计）。

每个阶段必须交三样东西，缺一样即视为未完成：

1. **冻档增量**（设计稿的 diff 段落）
2. **falsifier 结果**（实测数字，不是陈述）
3. **回滚指令**（一行能执行的配置/提交回退）

## V1 · 档位机制（0.9.0 第一个可发布切片）

**动机**：把"权限面"这件事立起来，但**不合并任何语义**——此时 core 只是 legacy 减去 7 张别名/诊断名片。

| 动作 | 产出 |
|---|---|
| `src/shared/surface.ts`：`Surface` 类型 + `TOOL_SURFACES` 表 + `visibleUnder()` | 单一可见性来源 |
| `config.surface`（volatile，默认 `legacy`） | 热切换 |
| `createMcpServer(bridge, surface)` + `registerBridgeTools(server, bridge, surface)` | 注册期过滤 |
| `health.surface = { tier, tool_count, tools_sha256 }` | 客户端可自证清单变化 |
| 四条车道参数化（CLI / golden / plugin-lifecycle / boot-smoke） | 每档契约 |
| 面板加 `{ key:'surface', kind:'enum' }`，显示**实测**字符与 token 区间 | 用户可感知 |

**此阶段的 core = 15 个名字，全部来自今日已有的 22 个**（`get_session` 仍独立存在，尚未合并）。

**2+2+1 审查重点**
- 必答题：档位是权限面还是显示层？（答：权限面，`mcp.js:70` / `:102-109`）
- C 席重点：切档瞬间旧名从可用变 `not found`，运维风险如何降？（设计稿要求面板显式二次确认 + 一行回滚）

**放行门槛**：F4（热切换）、F5（无诱导）、F7（每档每工具被驱动）、M1 全绿。

**回滚**：面板/配置把 `surface` 切回 `legacy`，立即生效，无需重启。

## V2 · 读合并与散文压缩（0.9.0 主体，风险最高）

**动机**：真正拿到 −44% 的固定成本。**这是唯一会改变响应形状的阶段。**

| 动作 | 产出 |
|---|---|
| `get_task_status` 加 `detail=status\|session\|both`（默认 `status` = 今日形状） | 吸收 `get_session` |
| 散文压到 desc≤175 / 参数说明≤70 | core → 10,895 |
| 修 D-2（4 处诱导隐藏名的文字） | core 档不再指向不可用工具 |
| 20 条剧本 ×2 档，first-choice accuracy 对照 | F10 |

**放行门槛（缺一不发）**
1. F3：默认 `detail='status'` 响应体积不超今日 `get_task_status` 的 ±10%（基线 ≈450 字符）
2. F9：合并后 workspace 锁释放副作用仍在
3. F2：`detail='session'` 键集 ⊇ 今日 `get_session`；`detail='status'` 键集 == 今日 `get_task_status`
4. F8：同名工具参数名集合逐字相等
5. F10：core 档选错工具率不高于 legacy 档（差 ≥1 条即回退到 desc≤260）
6. F1：core ≤ 11,000

**2+2+1 审查重点**
- P 席：`detail` 的默认值是否会让模型永远只用默认、拿不到消息？（需要描述里给出"何时传 session"的判据）
- C 席：**轮询税**——合并最热的读路径是否反而让运行时成本上升？（这是 C2 的 5 分攻击，必须有实测而非论证）

**回滚**：`surface: legacy` 即回到今日行为（`get_session` 仍在 legacy 档，`detail` 默认为 `status`）。

## 阶段依赖图

```
V0 (尺子+清障)
 └─▶ V1 (档位机制, core=15 无合并)
      ├─▶ V2 (合并+压缩)  ── 门槛 6 条，任一红则只发 V1
      └─▶ V3 (文档/默认面) ── 依赖 V2 的最终工具面
```

**关键约束**：V2 失败时，0.9.0 仍可只发 V1 —— 那是一个"能省 24%、零语义变更"的版本；**不允许为了达成 −44% 而降低 V2 的门槛**。

## 每阶段的固定动作（模板）

| 步骤 | 谁 | 产出 | 时限纪律 |
|---|---|---|---|
| 1. 两稿 | P1、P2 独立作业，不共享上下文 | `/tmp/*/P1.md`、`P2.md` | 停挖即收尾，宁可留 TODO |
| 2. 汇总 | 裁判 | `MERGED.md`（含偏差记录） | 必须复算两席的数字，不数票 |
| 3. 两审 | C1、C2 独立攻击 | `C1.md`、`C2.md`（每条带证据 + 强度分） | 不给替代方案不算合格 |
| 4. 冻档 | 裁判 | 设计稿 diff | 每条裁决附证据锚 |
| 5. 实现 | 执行 | 代码 + 测试 | 全绿 |
| 6. 归档 | 执行 | CHANGELOG + 实测数字 | 不绿不进档 |

**留痕要求**：被证伪的主张必须写进冻档的"本轮记录"一节——**错的判断比对的判断更有信息量**。
